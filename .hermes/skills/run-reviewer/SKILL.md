# Run Reviewer

Drive the reviewer tab of the two-agent PR loop for one issue. Same
state-machine principle as `run-implementer` (the PR thread decides),
but the reviewer owns steps 2, 4, and 5: Round 1 review, delta
re-review, and sign-off. The implementer tab runs `run-implementer`
on the same PR; the two never read each other's chats.

## Prerequisites

- The `implement` and `two-axis-review` skills installed at
  `~/.agents/skills` (user-level) or `.agents/skills`
  (project-level). This skill delegates the review process by
  reading `two-axis-review`'s SKILL.md; if it is missing, stop and
  report — do not improvise the process.
- `gh` authenticated against the repo's remote.

## Shared protocol — both tabs (keep in sync with run-implementer)

X = the issue number from the invocation. One system per issue; other
systems may run other issues concurrently.

- The GitHub PR is the ONLY channel between implementer and reviewer.
  Every plan, status, and verdict is a comment on the PR, prefixed
  "Round N: …" (N = round number). Always read the LATEST comment on
  the thread before acting — there may be several.
- Branch `feat/<X>-<slug>`, worktree `wt/<X>`, opened from the latest
  fetched base branch. The base resolves as: explicit `--base
  <branch>` > the found PR's `baseRefName` > `main`. If `wt/<X>` or
  the branch already exists: verify it is this issue's own stale
  artifact before reusing; if it looks foreign, stop and ask the user
  — never reuse or delete another system's worktree.
- PR body template: `Closes #<X>` plus `## Summary` (what and why,
  2–5 lines), `## Test plan` (commands run + results), `## Notes`
  (anything the reviewer should know).
- Verification gauntlet (fullstack-coder): typecheck regularly,
  targeted tests after each change, full suite once at the end;
  `test:e2e` when UI behavior changed; `docker build` when deployment
  output changed.
- Multi-instance isolation — other two-agent systems may work other
  issues in this repo right now:
  - Namespace everything with #<X>: worktree, branch, container
    names `n<X>-…`, paseo agents, handoff files.
  - The shared clone is never checked out to a feature branch —
    worktrees only. `git fetch origin` before every diff or merge;
    never trust a stale ref.
  - Ports: allocate dynamically at bind time (port 0, or verify free
    with `ss -ltn` immediately before binding). Never defaults, never
    remembered ports. Even if the containers you need exist, create
    your own instance on your own port.
  - paseo agents: name them `n<X>-<task>`, record the IDs, and only
    stop/archive your own (`paseo ls` to confirm ownership first).
  - Handoff docs: per-issue filenames (`handoff-<X>-round<M>.md`);
    check for existing handoff files for your issue before writing.
  - Before merging: re-fetch the base and re-check mergeability —
    another PR may have merged since your last check. After merging:
    attribute any base CI failure to your own merge commit before
    touching anything.
- Loop cap: 3 review rounds max; if exceeded, escalate to the user
  with a summary. The override section below can force more.

### Agent-comment markers

Every comment this loop posts — to a PR or an issue thread: review,
action plan, fixes-ready, rebased note, sign-off, close-out, blocked
warning, follow-up body — carries the marker: a visible prefix line
plus a hidden machine block at the very top of the comment, before
any content.

```text
🤖 [AI · <role> · R<N>]

<!-- @agent-comment v1
role: <implementer|reviewer>
run: <run-id>
issue: <X>
round: <N>
generated-by: run-reviewer
-->
```

- The run-id is short hex, generated by the implementer in Step 1
  and first embedded in the Round 1 comment; every later comment in
  the loop reuses it. The reviewer derives it from the thread — the
  two tabs never exchange it outside the PR.
- Authorship rule: comments post under whatever account runs the
  tab — the same user for both tabs, or user A (implementer) and
  user B (reviewer). Never infer role from the comment author; read
  the marker. The posting account needs comment (write) permission
  on the repo; posting identity is a deployment choice — your
  account today, a PAT or GitHub App later. The marker keeps the
  loop legible under any identity.
- Reading rule: unmarked comments are human; marked comments are
  automated. Consider human comments plus marked comments whose
  issue matches <X> (and whose run matches, once you know it).
  Ignore marked comments for other issues — other systems run
  concurrently.
- Handoff docs (`handoff-<X>-*.md`) are a same-machine convenience;
  when the tabs run under different accounts or machines, skip them
  — the marked PR thread carries everything.

## Entry flow — detect the step from the PR thread

1. Parse the invocation: issue number X (required); optional
   `step N` and `round M` overrides (see Override) and optional
   `--base <branch>`.
2. Find the PR: `gh pr list --head feat/<X>-*`, or search
   `Closes #<X>`. Sweep PRs (batch follow-up cleanup) live on
   `chore/sweep-*` branches and are found only via the Closes
   search — any issue in the batch resolves to the same PR. If no
   PR exists, the implementer has not opened one — report that the
   user should run `/run-implementer` in the implementer tab.
3. Read the full thread: description, round comments, review
   comments, verdicts, and the SHA each review states it reviewed.
   Extract the run-id from the Round 1 marked comment's hidden block
   — all your comments reuse it. If no marked Round 1 comment
   exists, report that the implementer has not posted it; the loop
   cannot start without its run-id. For a sweep PR, match marked
   comments by run-id (their `issue:` field carries `sweep-<date>`,
   not a single issue number).
4. Verify the PR's current head: compare `gh pr view --json
   headRefOid` with your fetched SHA; if they differ, re-fetch and
   review the real head.
5. Route by the table below.

| Detected state | Route |
|---|---|
| No PR for the issue | Report: implementer tab should run `/run-implementer` |
| PR open, Round 1 "implementation ready" present, no review comment yet | Step 2 — Round 1 review |
| Latest review = FINDINGS REMAIN, fixes-ready comment after it | Step 4 — re-review (round N+1) |
| Latest review = FINDINGS REMAIN, no fixes after it | Report: implementer tab should run `/run-implementer` (Step 3) |
| Sign-off comment already posted | **Hard stop** — report loop complete; implementer tab should run `/run-implementer` (Step 6, merge & close). Do not re-review or re-post |
| Latest review = APPROVED | Step 5 — sign-off |
| PR merged | Report: loop complete — implementer tab runs cleanup (Step 7) |

## Process

### Step 2 — Round 1 review

1. Read the `two-axis-review` skill's SKILL.md and follow its process:
   the two-axis review (Standards + Spec) as parallel sub-agents,
   fixed point = merge-base with the base branch:
   `git fetch origin <base> && git diff $(git merge-base origin/<base> <head-branch>)...<head-branch>`
   where `<base>` is the PR's base (`gh pr view --json baseRefName`),
   overridden by an explicit `--base <branch>`; `<head-branch>` is
   the PR's actual head —
   `origin/feat/<X>-<slug>` for a single-issue PR, `origin/chore/sweep-*`
   for a sweep batch (resolve via `gh pr view --json headRefName`).
   The spec is issue #<X>, fetched per `docs/agents/issue-tracker.md`.
   For a sweep PR, the spec is the union of the batch's issues.
2. On top of `two-axis-review`: verify the PR's test plan was actually
   executed (check CI results; a missing gauntlet is itself a
   finding); ensure no regressions (full test suite must pass) and
   new behavior is covered by tests (unit minimum; integration/e2e
   where behavior crosses boundaries); run the consistency check —
   flag anywhere the change broke coherence between code, docs,
   comments, repo rules, and the issue's objectives.
3. Post "Round 1 review — reviewed at <SHA>" with the fixed
   structure:
   `## Standards — <count> findings` (per file/hunk: violation or
   judgement call, citing the standard or smell)
   `## Spec — <count> findings` (missing / wrong / scope creep,
   quoting the issue)
   `## Blocking` (must-fix before merge)
   `## Non-blocking` (nits, suggestions, follow-up candidates)
   `## Verdict` — APPROVED, or FINDINGS REMAIN with the blocking
   list.
4. Do not APPROVE with open blocking findings.
5. Paste the complete review in chat for the user.
6. For a sweep PR, the review covers the whole batch as one delta —
   report per-issue where the diff maps to separate follow-ups.

**Done when:** the review comment is posted with the reviewed SHA and
a verdict, and the complete review is shown in chat.

### Step 4 — Re-review (round N+1)

1. Read the thread: the LATEST fixes-ready comment and your own
   previous reviews (each states the SHA it reviewed).
2. `git fetch origin`; verify the branch head matches the
   fixes-ready comment's stated SHAs. If the head moved beyond them
   (e.g. a conflict-resolution merge), review that extra delta too
   and say so in your comment.
3. Delta-review: `git diff <last-reviewed-SHA>...<head-branch>`
   where `<head-branch>` resolves as in Step 2 — focus on the
   fixes, not the whole diff.
4. For each prior finding, state RESOLVED / PARTIALLY / NOT
   ADDRESSED, citing the code.
5. Regression check: full test suite must pass; new features still
   covered; the fixes introduced no new issues (run the gauntlet if
   CI does not).
6. Implementer push-back: if they rejected a finding with reasoning,
   re-read the code — agree, or push back exactly once. Do not
   re-litigate settled points.
7. Consistency check (code, docs, comments, rules, objectives) on
   the delta.
8. Post "Round N+1 review — reviewed at <SHA>" with the same
   structure as Step 2, plus a "Previous findings" table (finding →
   status). Verdict: APPROVED or FINDINGS REMAIN.
9. APPROVED → submit the formal GitHub review approval.
   FINDINGS REMAIN → list blocking items; the implementer does the
   next round.
10. Loop cap: after 3 review rounds without convergence, escalate to
    the user with a summary (unless overridden).
11. Paste the complete review in chat.

**Done when:** the delta is reviewed against the anchor SHA, the
findings table is posted, a verdict is given, and the formal approval
is submitted when APPROVED.

### Step 5 — Sign-off (loop exit)

1. If your sign-off comment is already on the thread, **hard stop**:
   report loop complete and redirect the user to the implementer tab
   (`/run-implementer`, Step 6, merge & close). Do not re-review or
   re-post.
2. `git fetch origin` — if the PR head changed since your approval
   (e.g. the implementer pushed a rebase), re-review the delta
   before signing off; your approval does not travel to a new SHA.
3. Confirm all PR checks are green and the merge target is the base
   branch (resolved as in Step 2 — `baseRefName`, overridable with
   `--base`).
4. Final scan of the whole diff — one pass. If you find a new
   blocker, revoke the approval and post "Round N+1: findings"; do
   NOT let it merge.
5. Post "Round N verdict: APPROVED — reviewed at <SHA>. No blocking
   findings. Ready to merge — implements #<X>." (for a sweep PR,
   "implements the batch's issues" instead of a single #<X>).
6. Ensure the formal GitHub review approval is in place.
7. Tell the user in chat: approved — the implementer tab should run
   `/run-implementer` (Step 6, merge & close).

**Done when:** the sign-off comment is posted, the formal approval is
submitted, and the user is told to run the implementer.

## Override

- `step N` forces a specific step regardless of detected state —
  e.g. blowing past the 3-round cap:
  `/run-reviewer #123 step 4 round 5`.
- `round M` overrides the round number used in comments and the cap
  check.
- `--base <branch>` overrides the base branch read from the PR
  (`baseRefName`). Use it when reviewing a PR whose base is not what
  you expect (e.g. a mis-targeted PR, or a PR whose base you
  disagree with). The reviewer always reviews an existing PR; if no
  PR exists, report that the implementer should open one first.
- Forcing a step never bypasses a verdict's gate: an APPROVED PR can
  be forced back into Step 4 for another look, but Step 5 still
  refuses to sign off a head SHA you have not reviewed.

## Common pitfalls

1. Reviewing a stale head — fetch first, then check `headRefOid`.
2. Re-reviewing the whole diff instead of the delta since the
   last-reviewed SHA.
3. Losing the anchor — every review comment states the SHA it
   reviewed.
4. APPROVING with open blocking findings.
5. Re-litigating implementer push-back beyond one exchange.
6. Signing off a head SHA you have not reviewed (Step 5 gate).
7. Re-invoking after sign-off — the hard-stop row exists; report and
   redirect, never re-review or re-post.
8. Looking for a sweep PR on `feat/<X>-*` — sweep branches are
   `chore/sweep-*`; find them via the Closes search.
9. Reviewing against the wrong base — always resolve the base
   (`baseRefName`, overridable with `--base`) before computing the
   merge-base fixed point; a stale base silently diffs the wrong
   tree.
10. Letting the shared protocol drift — when you edit the protocol
    block here, apply the same edit to `run-implementer`.

## Verification checklist

- [ ] PR head fetched and verified against `headRefOid` before
      reviewing
- [ ] Review comment posted with the reviewed SHA, the fixed
      structure, and a verdict
- [ ] Step 4: delta against the last-reviewed SHA, findings table,
      regression + consistency checks
- [ ] Step 5: head re-verified, formal approval submitted, user told
- [ ] Base resolved correctly (override > baseRefName > main) before
      any diff or merge
- [ ] Complete review pasted in chat each round
- [ ] Loop cap respected, or overridden explicitly
