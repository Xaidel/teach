# Run Implementer

Drive the implementer tab of the two-agent PR loop for one issue. The
PR thread is the state machine: this skill detects where the loop is
and runs the matching step — implement (1), resolve review findings
(3), merge & close (6), or cleanup (7). The reviewer tab runs its own
skill (`run-reviewer`) on the same PR; the two never read each
other's chats.

## Prerequisites

- The `implement` and `code-review` skills installed at
  `~/.agents/skills` (user-level) or `.agents/skills`
  (project-level). This skill delegates their processes by reading
  their SKILL.md files; if either is missing, stop and report — do
  not improvise the process.
- `gh` authenticated against the repo's remote.

## Shared protocol — both tabs (keep in sync with run-reviewer)

X = the issue number from the invocation. One system per issue; other
systems may run other issues concurrently.

- The GitHub PR is the ONLY channel between implementer and reviewer.
  Every plan, status, and verdict is a comment on the PR, prefixed
  "Round N: …" (N = round number). Always read the LATEST comment on
  the thread before acting — there may be several.
- Branch `feat/<X>-<slug>`, worktree `wt/<X>`, opened from the latest
  fetched base branch. The base resolves as: explicit `--base
  <branch>` > the found PR's `baseRefName` > `main`. If `wt/<X>` or
  the branch already exists: verify it is this issue's own stale
  artifact before reusing; if it looks foreign, stop and ask the user
  — never reuse or delete another system's worktree.
- PR body template: `Closes #<X>` plus `## Summary` (what and why,
  2–5 lines), `## Test plan` (commands run + results), `## Notes`
  (anything the reviewer should know).
- Verification gauntlet (fullstack-coder): typecheck regularly,
  targeted tests after each change, full suite once at the end;
  `test:e2e` when UI behavior changed; `docker build` when deployment
  output changed.
- Multi-instance isolation — other two-agent systems may work other
  issues in this repo right now:
  - Namespace everything with #<X>: worktree, branch, container
    names `n<X>-…`, paseo agents, handoff files.
  - The shared clone is never checked out to a feature branch —
    worktrees only. `git fetch origin` before every diff or merge;
    never trust a stale ref.
  - Ports: allocate dynamically at bind time (port 0, or verify free
    with `ss -ltn` immediately before binding). Never defaults, never
    remembered ports. Even if the containers you need exist, create
    your own instance on your own port.
  - paseo agents: name them `n<X>-<task>`, record the IDs, and only
    stop/archive your own (`paseo ls` to confirm ownership first).
  - Handoff docs: per-issue filenames (`handoff-<X>-round<M>.md`);
    check for existing handoff files for your issue before writing.
  - Before merging: re-fetch the base and re-check mergeability —
    another PR may have merged since your last check. After merging:
    attribute any base CI failure to your own merge commit before
    touching anything.
- Loop cap: 3 review rounds max; if exceeded, escalate to the user
  with a summary. The override section below can force more.

### Agent-comment markers

Every comment this loop posts — to a PR or an issue thread: review,
action plan, fixes-ready, rebased note, sign-off, close-out, blocked
warning, follow-up body — carries the marker: a visible prefix line
plus a hidden machine block at the very top of the comment, before
any content.

```text
🤖 [AI · <role> · R<N>]

<!-- @agent-comment v1
role: <implementer|reviewer>
run: <run-id>
issue: <X>
round: <N>
generated-by: run-implementer
-->
```

- The run-id is short hex, generated by the implementer in Step 1
  and first embedded in the Round 1 comment; every later comment in
  the loop reuses it. The reviewer derives it from the thread — the
  two tabs never exchange it outside the PR.
- Authorship rule: comments post under whatever account runs the
  tab — the same user for both tabs, or user A (implementer) and
  user B (reviewer). Never infer role from the comment author; read
  the marker. The posting account needs comment (write) permission
  on the repo; posting identity is a deployment choice — your
  account today, a PAT or GitHub App later. The marker keeps the
  loop legible under any identity.
- Reading rule: unmarked comments are human; marked comments are
  automated. Consider human comments plus marked comments whose
  issue matches <X> (and whose run matches, once you know it).
  Ignore marked comments for other issues — other systems run
  concurrently.
- Handoff docs (`handoff-<X>-*.md`) are a same-machine convenience;
  when the tabs run under different accounts or machines, skip them
  — the marked PR thread carries everything.

## Entry flow — detect the step from issue + PR state

Why the PR thread is the state machine: the round number, the latest
verdict, and the reviewed SHAs all live in the thread, so the loop
never needs a side ledger. Block state lives on the issue, not the
thread — hence the two-input read below.

1. Parse the invocation. If it is `sweep` (no issue number; optional
   `--base <branch>` to target a non-main base for the batch), skip
   directly to the Sweep lane below. Otherwise: issue number X with
   optional `step N` and `round M` overrides (see Override) and
   optional `--base <branch>` to target a non-main base branch.
2. Read the issue: `gh issue view <X>` — state (OPEN/CLOSED),
   labels, and body. Treat the issue as BLOCKED when a blocked
   label, an explicit blocker reference in the body, or the user
   says so. When in doubt, ask the user — one question.
3. Find the PR: `gh pr list --head feat/<X>-*`, or search
   `Closes #<X>` (sweep PRs use `chore/sweep-*` branches and are
   found by the Closes search). If the issue is a follow-up —
   title prefix `[follow-up:<Y>]` or the `follow-up-issue` label —
   read the parent issue/PR thread for the review context that
   spawned it and carry it into the step.
4. Read the PR thread (description, round comments, verdicts,
   reviewed SHAs) if a PR exists. For a sweep PR, match marked
   comments by run-id (their `issue:` field carries `sweep-<date>`,
   not a single issue number).
5. Route by the table below.

| Detected state | Route |
|---|---|
| Issue BLOCKED | **Blocked sub-flow** below — no worktree, no PR |
| Issue CLOSED, PR merged | Step 7 — cleanup & close-out (idempotent: already clean → report done) |
| Issue CLOSED, no PR | Report: nothing to do — issue was closed without a PR (do not re-open) |
| No PR, issue open, not blocked | Step 1 — implement |
| PR open, review = FINDINGS REMAIN, no fixes comment after | Step 3 — resolve |
| PR open, review = FINDINGS REMAIN, fixes comment after | Report: reviewer tab should run `/run-reviewer` (Step 4 — re-review) |
| PR open, review = APPROVED, no sign-off comment | Report: reviewer tab should run `/run-reviewer` (sign-off) |
| PR open, no review comment yet | Report: reviewer tab should run `/run-reviewer` (Round 1) |
| PR open, sign-off comment present | Step 6 — merge & close |

### Blocked sub-flow

1. **Warn** the user what is blocking #<X> (label, body reference, or
   their own statement).
2. **Present the conservative alternative**, concretely, and let the
   user choose:
   - Cleanup slice — the smallest unblocked work on the same
     feature that does not touch the blocker. Do it on its own
     branch as scoped commits; never a PR that claims to close
     #<X>.
   - Follow-up issues — file issues for anything discovered while
     scoping (blocker causes, tangents). Create them with the same
     follow-up stamping as Step 7 — `[follow-up:<X>]` title +
     `follow-up-issue` label + `Part of #<X>` body + parent
     task-list item — so the sweep lane detects them.
   - Honest pause — if the work really must wait, say so plainly.
     Do not fake progress.
3. **Execute the user's choice.** If they insist on implementing
   despite the block, comply and record the warning in the issue
   thread.

**Done when:** the user is informed, the chosen alternative is
delivered (or the pause stated), and no PR claims to close #<X>.

## Process

### Step 1 — Implement

1. Confirm the issue is unblocked (the entry flow ran the blocked
   check; re-run it if the route was forced).
2. Generate the run-id for this loop — short hex, e.g.
   `python3 -c 'import secrets; print(secrets.token_hex(3))'`. It
   marks every comment this loop posts (see Agent-comment markers).
3. Resolve `<base>` per the shared protocol — at first creation no
   PR exists yet, so it is the `--base` override or `main`.
   `git fetch origin <base>`; create worktree `wt/<X>` with branch
   `feat/<X>-<slug>` from the freshly fetched base.
4. Read the `implement` skill's SKILL.md and follow its process in
   this session: implement per the issue/spec, /tdd at pre-agreed
   seams, typecheck regularly, targeted tests, and relevant authoring
   skills (fullstack-coder). Use paseo agents (`paseo run`, named
   `n<X>-<task>`) for concurrent work; record their IDs; stop/archive
   them when done.
5. Run the verification gauntlet; fix anything it catches.
6. `git fetch origin <base>` again; if the base moved, rebase/merge
   it in and re-run the gauntlet — the PR must sit on the current
   base.
7. Commit referencing #<X>; push; open the PR with the body template
   from the shared protocol.
8. Post "Round 1: implementation ready for review" with the marker —
   what was built, gauntlet results, areas you want scrutiny on.
9. Write the handoff doc for the reviewer tab at
   `handoff-<X>-round1.md` (OS temp dir) — point at the PR and
   issue; do not duplicate their content.

**Done when:** the PR is open with the body template, the Round 1
comment is posted, and the handoff doc is written.

### Step 3 — Resolve review findings

1. Read the LATEST review comment (there may be several on the
   thread). Before any action, build a full holistic understanding:
   the entire PR diff, every review comment, the surrounding modules
   they touch, and how the change integrates with existing code,
   docs, and repo rules.
2. `git fetch origin`; if the PR head moved since the review, note it
   — the review's stated SHA is your anchor.
3. Per finding: accept, or push back in the PR thread with concrete
   reasoning (quote the code, cite the spec or standard). No silent
   ignores.
4. Post "Round N+1: action plan" BEFORE changing code — per finding:
   accept/reject, the proposed fix, files it touches. This is a plan
   the reviewer will see, not a gate.
5. Implement the accepted fixes on the same branch. Use /tdd where it
   helps. Re-run the full verification gauntlet.
6. Commit and push. Post "Round N+1: fixes ready" — each finding →
   change (commit SHAs) plus gauntlet results.
7. If the review already APPROVED: do NOT change code — go to Step 6.

**Done when:** the action plan was posted before any edit, the fixes
are pushed, the fixes-ready comment carries the SHAs, and the gauntlet
is green.

### Step 6 — Merge & close

1. Verify all PR CI checks are green. If the gauntlet was not run on
   the branch, run it now.
2. `git fetch origin <base>` IMMEDIATELY before merging — other PRs
   merge while you work. If the base moved and the branch is behind,
   merge the base in, re-run the gauntlet, push, and post "Round N+1:
   rebased on latest base" so the reviewer's delta anchor stays
   honest. If the conflict resolution was non-trivial (judgment, not
   mechanical), request reviewer re-confirmation before merging. Use
   /resolving-merge-conflicts if conflicts appear; a concurrent PR's
   changes may collide — resolve per repo conventions and coordinate
   in the PR thread.
3. Merge the PR (squash per repo convention) — the merge message
   contains "Closes #<X>" (for a sweep PR, the full `Closes` list).
   Re-check mergeability right up to the
   click; if branch protection rejects, return to step 2.
4. Confirm issue #<X> auto-closed; if not, close it manually with a
   resolution summary (what shipped, where).
5. Watch post-merge CI on the base. ATTRIBUTE BEFORE ACTING: record
   your merge SHA (`gh pr view --json mergeCommit`); on failure run
   `git log -1 origin/<base> --format='%H %s'`. If the red commit is
   yours: fix forward immediately. If it is another PR's merge: do
   not fix their code silently — report it to the user, name the
   offending commit, and coordinate.
6. Post the close-out comment: shipped behavior, review history
   (rounds + what changed), test evidence.

**Done when:** merged with "Closes #<X>", the issue is closed, the
post-merge CI is attributed (and fixed if yours), and the close-out
comment is posted.

### Step 7 — Cleanup & close-out

1. If the worktree and branch are already gone and your close-out
   handoff doc exists, **hard stop**: report the loop is complete
   and do not re-file follow-ups or re-write handoffs.
2. Remove worktree `wt/<X>`; delete branch `feat/<X>-<slug>` (local
   + remote, per repo convention). Double-check the branch name
   before deleting — never delete a branch you did not create.
3. Stop/archive only the paseo agents whose IDs you recorded
   (`paseo ls` first to confirm none are shared or another issue's).
4. Remove your temp/handoff files (`handoff-<X>-*.md`). Leave every
   other file alone.
5. File follow-up issues for anything the review surfaced that was
   out of scope for #<X> (scope creep, tech debt). Each follow-up:
      - title `[follow-up:<X>] <summary>`, label `follow-up-issue`
      - body starts `Part of #<X>`, plus "Follow-up from PR #<pr>
        (Round N review)" and the review context that spawned it
      - after creation, append `- [ ] #<new-number>` to the parent
        issue #<X>'s body (a task list — GitHub renders the child
        as "Part of #<X>" and ticks the checkbox when it closes)
6. Write the close-out handoff doc (`handoff-<X>-done.md`): what
   shipped, PR/issue links, follow-ups.
7. Report to the user: merged, issue closed, cleanup done,
   follow-ups filed.

**Done when:** only your artifacts are removed, follow-ups are filed
and linked, and the report is given.

### Sweep lane — batch follow-up cleanup

Small, independent follow-up issues (`[follow-up:<X>]` title prefix
or `follow-up-issue` label, filed by Step 7) are handled as one
batch: one worktree, one branch, one PR, one review loop. Invoke
with `/run-implementer sweep` (no issue number).

1. **Enumerate the batch** — list open follow-ups: `gh issue list
   --state open --label follow-up-issue` plus `gh issue list
   --state open --search "[follow-up:"` (the label may be missing
   in repos without the scheme). Merge and dedupe.
2. **Present the batch** to the user for confirmation — they may
   exclude any issue. Flag any batch member that is itself BLOCKED
   (label, body reference, or user statement) and exclude it from
   the batch — route it through the Blocked sub-flow instead. If
   the batch is empty, report and stop.
3. **One batch unit** — worktree `wt/sweep-<date>`, branch
   `chore/sweep-<date>-<slug>` from the latest fetched base (same
   base resolution as single-issue loops: `--base` > PR
   `baseRefName` > `main`; at batch creation no PR exists yet, so
   `--base` or `main`).
   Namespace everything by the batch: containers `nsweep-…`, paseo
   agents `nsweep-<task>`, handoff file `handoff-sweep-<date>.md`.
   Generate the batch run-id here (see Agent-comment markers) — it
   marks every comment the sweep posts.
4. **Implement each issue as its own scoped commit**, each commit
   referencing its issue (`#<X>`). Keep the commits independent —
   no cross-issue coupling; the diff stays reviewable per issue.
5. Run the verification gauntlet once over the whole batch.
6. `git fetch origin <base>` again; if the base moved, rebase/merge
   it in and re-run the gauntlet.
7. **One PR closing all**: push; open the PR with body
   `Closes #<X>, Closes #<Y>, …` plus the body template (Summary /
   Test plan / Notes) covering the whole batch. Post "Round 1:
   implementation ready for review" with the marker — for the
   batch, the marker's `issue:` field carries `sweep-<date>` (not
   a single issue number), and readers match sweep comments by
   run-id rather than issue.
8. Review loop runs exactly as a single-issue loop (Step 3 resolve,
   rounds, cap) — the reviewer finds the sweep PR via the
   `Closes #<X>` search. On APPROVED: merge (Step 6) — the merge
   closes every issue listed in the body. Then cleanup (Step 7) on
   the batch unit: remove `wt/sweep-<date>`, delete the branch,
   stop the batch's paseo agents, remove the batch handoff, write
   the batch close-out handoff (`handoff-sweep-<date>-done.md`),
   and file any follow-ups the sweep review surfaced (stamped
   `[follow-up:<parent>]` per the issue they concern, per Step 7's
   stamping rules).

**Done when:** the batch PR is open closing every follow-up in the
batch, or the batch is merged, every listed issue is closed, and the
batch artifacts are removed.

## Override

- `step N` forces a specific step regardless of detected state —
  e.g. blowing past the 3-round cap:
  `/run-implementer #123 step 3 round 4`.
- `round M` overrides the round number used in comments and the cap
  check.
- Forcing a step does NOT bypass the unblocked gate: the blocked
  check runs inside Step 1 and the Blocked sub-flow. Only explicit
  user consent ("implement anyway") proceeds, recorded in the issue
  thread.
- `sweep` is a lane, not a step — it cannot be combined with
  `step N`; use `/run-implementer sweep` on its own.
- `--base <branch>` targets a non-main base branch: the worktree
  base, rebase/merge target, merge-target check, and post-merge CI
  attribution all follow it. Resolution: `--base` > found PR's
  `baseRefName` > `main`. Without `--base`, Step 1 assumes `main`
  (no PR exists yet at first creation) and later steps read the
  PR's actual base.

## Common pitfalls

1. Treating "no PR" as "implement" without checking the blocked
   state first.
2. Trusting a stale fetch of the base or the PR head — fetch before
   every diff and merge.
3. Reusing or removing another system's worktree, branch, or paseo
   agents.
4. Editing code after approval (the Step 3 guard).
5. Posting the action plan after editing instead of before.
6. Merging without re-fetching the base — a concurrent PR may have
   merged.
7. Fixing a red base commit that is not yours — attribute first.
8. Re-invoking after cleanup — Step 7 is idempotent; if the loop is
   already closed out, report done and do not re-file anything.
9. Sweeping without user confirmation — present the batch, let the
   user exclude issues, then proceed.
10. A sweep PR that does not close every issue it touches — the
    body's `Closes` list must match the batch exactly, or the merge
    silently leaves follow-ups open.
11. Reusing another system's sweep worktree — `wt/sweep-<date>` is
    a batch namespace like any other; verify ownership before
    reuse.
12. Letting the shared protocol drift — when you edit the protocol
    block here, apply the same edit to `run-reviewer`.

## Verification checklist

- [ ] Entry flow read the issue state AND the PR thread before
      routing
- [ ] Blocked issues went through the Blocked sub-flow — no worktree,
      no PR claiming to close #<X>
- [ ] The routed step ran to its completion criterion; comments use
      the "Round N" prefix and carry SHAs where promised
- [ ] Step 6: fetched the base immediately before merging; merged
      with "Closes #<X>"; issue closed; CI attributed
- [ ] Step 7: only your artifacts removed; follow-ups filed with
      `[follow-up:<X>]` title + `follow-up-issue` label + parent
      task-list link
- [ ] Sweep lane: batch presented for confirmation; one PR whose
      `Closes` list matches the batch exactly; batch artifacts
      removed
- [ ] Handoff docs written where the step calls for them (round 1,
      close-out)
